# Forza Motorsport Linux v0.1 Publication Design

Date: 2026-09-02
Status: Approved

## Decision

Publish the first source-only release from the protocol generation that is
actually running Forza Motorsport locally. Keep the newer WineGDK and Xodus
work as a separate experimental line until it independently passes the same
live-game matrix.

This design supersedes the 2026-08-31 publication design for release status,
provenance, verification, and publication sequencing. The earlier document
remains historical context.

## Purpose

Provide a professional, auditable Linux setup for the Steam edition of Forza
Motorsport, AppID 2440510, while keeping three different kinds of evidence
unambiguously separate:

1. behavior confirmed in the current live installation;
2. behavior proven only by automated or hermetic tests;
3. behavior that failed or still requires a current manual retest.

The project must be useful to players without implying ordinary upstream
Proton support or redistributing Microsoft components.

## Release boundary

Version 0.1 contains only original scripts, manifests, patches, tests, and
documentation. GitHub-generated source archives are the only release
artifacts. No prebuilt Wine, Proton, Xodus, DLL, SYS, EXE, game asset, account
state, or runtime log is attached.

The supported v0.1 line is the reconstructed legacy protocol generation:

- Xodus public source commit `7b236772297b3475ea4f3cb830feb5b224f3064a`, which
  extends the live-proven legacy base with an explicit, action-time-revalidated
  Join action for every friend row.
- Wine/XGameRuntime base commit
  `a6e6199f81aeb8a96e8ff281e781f5eba2146fe7` plus the source changes that
  produced the currently working runtime.
- The current integration launcher, doctor, service lifecycle, exact-build
  patching, and transactional recovery work.

The newer source-reviewed pair remains experimental:

- WineGDK `d96a768e25f632b04a457e4cb9f585e89ef5d095`.
- Xodus `ee9db0f68122a9731b9b66cc24767693d1737f5c`.

Its hermetic tests are valuable evidence, but its live combinations produced
protocol rejection, flicker, or exit after the logo. It is not a v0.1 runtime
dependency and must not be described as live-working.

- Automatic receipt of unsolicited Xbox invite notifications is not
  supported. Invite and join through an explicitly opened social flow are a
  different capability.

## Repository architecture

### Integration repository

The integration repository is the only user-facing entry point. Its `main`
branch owns:

- the `forza-linux` per-session launcher;
- the disabled-by-default `xodus-forza.service` user unit;
- the read-only `forza-doctor` diagnostic;
- Steam launch-option generation;
- user-local install and uninstall;
- exact-build controller and storage fallback patches;
- recoverable runtime-component transactions;
- privacy, provenance, and publication tests;
- links to immutable component source revisions.

It does not vendor component source or compiled component artifacts.

### Component branches

Component work is published in the repository that owns the code:

- Xodus legacy source: a privacy-clean, one-commit public branch pinned to
  `3a26a6c` directly on parent `518a0eb`. Its tree contains the explicit Join
  action, the personal fixture-name scrub, and only deterministic formatting
  beyond the preserved private evidence tree.
- Working XGameRuntime source: a clean branch from `a6e6199` containing only
  the reviewed game UI, invite, socket, and lifecycle changes needed to
  reproduce the working protocol generation.
- Controller identity: a separate Wine branch and review item.
- Storage TRIM reporting: a separate Wine branch and review item.
- New WineGDK/Xodus bridge: separate experimental branches with the failed
  live matrix recorded.

No branch name is treated as a stable download location until its exact commit
is recorded in the publication manifest.

### Publication manifest

`docs/publication-manifest.toml` is the machine-readable release authority. It
records:

- exact component commits;
- source-tree or patch digests where a clean commit is not yet available;
- open-source build artifact hashes used for parity checks;
- each manual claim with one of `verified`, `experimental`, `rejected`, or
  `unresolved`;
- the verification date and environment boundary;
- public repository, branch, issue, and pull-request URLs after publication.

The integration commit is bound by the immutable `v0.1.0` tag and GitHub
release metadata after green CI. The manifest cannot contain its own final Git
commit without creating a self-referential hash cycle.

No release is created while any v0.1-required claim is `unresolved`.

## Source reconstruction

The working installation remains untouched while its source is reconstructed.
All work occurs in isolated Git worktrees.

The private Xodus evidence side starts from exact legacy commit `23da0ab`, adds
the reviewed Join action commit at `76cab766`, and ends at privacy-scrubbed tip
`45dc65b2`. Publication uses the privacy-clean one-commit snapshot `3a26a6c`
directly on upstream parent `518a0eb`; a clean release build must match its
recorded hashes and then pass equivalent automated and live behavior.

The XGameRuntime side starts from `a6e6199`. The existing dirty checkout is
evidence, not a publication branch. Its tracked diff and untracked source files
are copied into an isolated branch, split into reviewable commits, and tested.
Generated build-system files and unrelated Wine build output are excluded.

The reconstruction is accepted only when:

1. every intended source change is represented by a commit;
2. `git diff --check` and component tests pass;
3. a clean build succeeds from the recorded commit;
4. installed-artifact parity is explained and recorded;
5. the recoverable live installation passes the complete manual matrix.

## Installation and launch data flow

The public setup keeps Xodus session-scoped:

1. Steam invokes the generated launch-options line.
2. `forza-linux` validates private transaction state and takes the launch lock.
3. The launcher creates a one-shot mode-0600 ownership reservation.
4. The user unit consumes that reservation and starts Xodus.
5. The launcher waits for the exact Unix socket with a bounded timeout.
6. Steam's game command runs without reinterpreting user arguments.
7. On game exit, the launcher stops only the matching Xodus invocation it
   owns and removes only its proven orphaned socket.
8. A pre-existing Xodus service is preserved.

The unit remains disabled and has no install target. Xodus is not a permanent
login or desktop-session daemon.

KDE Wallet provides the Secret Service interface. The setup neither installs
nor recommends GNOME Keyring, and it does not enable plaintext credential
storage.

## Failure and rollback behavior

Every live component replacement uses the existing recoverable runtime
transaction. Before the first mutation it records source revisions, source and
destination hashes, modes, roots, and a digest-bound plan. It refuses to run
while Forza or the dedicated Xodus service is active.

If installation, daemon reload, launch, authentication, or the manual matrix
fails:

- the candidate is not accepted;
- rollback restores the exact prior open-source artifacts;
- the external Microsoft threading file and the game prefix remain outside
  the transaction;
- recovery material is retained until independently verified;
- the candidate branch remains experimental;
- no public release claim is upgraded to `verified`.

The live working baseline must never be overwritten merely to obtain a clean
build hash.

## Verification strategy

### Automated integration gates

The release candidate must pass:

- the complete `just verify` suite;
- repository privacy and forbidden-artifact policy tests;
- ShellCheck, shfmt, Ruff, REUSE, and systemd unit verification;
- install, uninstall, interruption, recovery, and rollback tests;
- `git fsck --full`;
- a full-history scan for private paths, identities, tokens, invite data, and
  prohibited binaries.

### Component gates

- Xodus: safe offline workspace tests, fixture-driven protocol tests, social
  UI keyboard/controller tests, and a clean release build.
- XGameRuntime: interface, XAsync, fragmented transport, lifecycle, invite
  registration, activation, and clean-build tests.
- Wine controller: physical XInput identity and Steam virtual-controller
  regression tests.
- Wine storage: full, header-only, short-buffer, and unrelated-property tests.

CI must not contact Microsoft or Xbox endpoints and must use synthetic account
and invite data.

### Manual live matrix

The same candidate installation must pass, in order:

1. cold launch with Xodus initially stopped;
2. online profile and content download;
3. controller navigation and driving;
4. controller disconnect and reconnect;
5. no AP702 warning;
6. Linux-to-Windows invite;
7. Linux join to a compatible Windows activity;
8. keyboard and controller operation in the social picker;
9. clean game exit with Xodus inactive and the socket absent;
10. a second successful launch without a system reboot.

Human observation is required for game UI, driving, invite, and join claims.
Process, socket, service, and artifact evidence is collected locally and
published only in redacted summary form.

## Upstream publication sequence

Publication proceeds only in this order:

1. freeze the evidence manifest and pass all local gates;
2. create the public integration repository and obtain green CI;
3. publish immutable component branches and record their exact commits;
4. update integration links and rerun CI;
5. coordinate social overlap in Xodus issue 94 and reference the existing
   xgameui and title-token work before opening review requests;
6. open controller and storage review items independently;
7. publish the newer WineGDK bridge as an AI-assisted experiment, not a merge
   proposal or v0.1 dependency;
8. post one concise, privacy-reviewed compatibility update to Proton issue
   7151;
9. create the source-only v0.1.0 tag and release after all links and claims are
   consistent.

No GitHub repository, fork, branch, issue comment, pull request, tag, or
release is created before a final publication review presents its exact target
and text.

## Privacy and legal requirements

- Do not publish friend identities, account handles, XUIDs, email addresses,
  authorization material, proof keys, invite URIs, or private socket payloads.
- Do not publish local usernames, home paths, private logs, or screenshots
  containing identifying UI.
- Do not commit or attach Microsoft DLLs, GameConfigHelper, game assets, or
  extracted proprietary source.
- Users must supply required Microsoft runtime material only from a licensed
  installation under terms applicable to them.
- Preserve upstream licenses and attribution for every source-derived patch.
- Describe the result as experimental and environment-specific, never as
  official Valve, Microsoft, Turn 10, Wine, GE-Proton, or Xodus support.

## Acceptance criteria

The design is complete when all of the following are true:

- the working protocol generation is represented by clean immutable source
  commits;
- a clean build and recoverable install pass the automated and manual gates;
- the publication manifest contains no unresolved v0.1-required claim;
- the integration and component histories pass privacy and licensing review;
- public documentation distinguishes verified, experimental, rejected, and
  unsupported behavior;
- every public link resolves to the exact reviewed revision;
- the source-only release contains no prohibited binary or private evidence;
- upstream messages are concise, non-duplicative, and scoped to the owning
  project.

## Non-goals

- Making the newer WineGDK/Xodus bridge part of v0.1 before a successful live
  matrix.
- General Proton compatibility or support for every distribution, GPU,
  controller, wheel, or Steam library layout.
- Permanent Xodus service enablement.
- Plaintext credential storage or GNOME Keyring installation.
- Automatic incoming Xbox invite notifications.
- Automatic modification of Steam's local configuration.
- Publishing the blog as part of this release cycle.
