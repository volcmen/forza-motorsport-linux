# SteamOS platform investigation — 2026-10-15

Later work: [composed preview build and packaging](composed-preview-build-2026-10-15.md) and [SteamOS lifecycle qualification](composed-preview-validation-2026-10-15.md). This record remains historical.

**Verdict: support is in development. This is not Steam Deck gameplay or a completed installer validation.**

## Environment and isolation

- Official Valve recovery image: `steamdeck-oobe-repair-20260707.10-3.8.14.img.bz2`, obtained from [Valve's recovery server](https://steamdeck-images.steamos.cloud/recovery/steamdeck-oobe-repair-20260707.10-3.8.14.img.bz2).
- Download SHA-256: `4254ee02ec34ae8add9aceef1881a2ce675a9d0176171df92e0eaa1bf014c594`. Decompressed image SHA-256: `f9aa0fa2dd618febf28a5e2a583d1e2b5a8ca3f1205be965da584602ac962f40`. These are locally computed identities, not a claim of Valve signature verification.
- QEMU/KVM, x86_64 host CPU, four vCPUs, 4 GiB RAM, OVMF firmware. No GPU passthrough.
- The recovery image had a separate qcow2 overlay. Valve's `repair_device.sh all` installed onto a newly created 64 GiB qcow2 disk exposed as a virtual NVMe device with serial `FORZA-TEST-ONLY`. No existing host disk, VM disk, Steam installation, or account directory was attached.
- The installed disk booted independently of the recovery disk, using the matching Valve kernel/initramfs and `steamos.efi=/dev/nvme0n1p2`. A serial autologin and `multi-user.target` were provisioned in the guest's `/etc` overlay. This bypassed graphical OOBE; Desktop Mode, Gaming Mode, and normal firmware boot were not tested.
- Source and the public release bundle were shared through a read-only 9p mount. QEMU user networking used `restrict=on`; there was no host network or Docker socket passthrough.

## Released native components

Tested the public `v0.2.0` bundle after checking its shipped manifest identity:
`68d7fc9e70a665c575f34432a5136e22bc07c840a028a52ec83b06f889c2b9b1`.
The three native executables require at most `GLIBC_2.39` according to their ELF
version requirements. The guest dynamic loader's `--list` command established:

| Component | Result |
| --- | --- |
| `xodus-service` | All shared libraries resolved. Service authentication/protocol behavior was not tested. |
| `xodus-cli` | Cannot load: `libwebkit2gtk-4.1.so.0` is missing. |
| `xodus-overlay` | Cannot load: `libadwaita-1.so.0` is missing. |

GTK4, SDL3, OpenSSL 3, and D-Bus library files were present. Resolving the first
missing dependency does not prove the rest of either GUI application's dependency
chain or UI works. No system packages were installed and SteamOS read-only mode
was not disabled. A tested user-space packaging solution is required before the
released GUI tools can be recommended on this SteamOS image.

## Installer boundaries

- Issue [#7](https://github.com/volcmen/forza-motorsport-linux/issues/7): the pinned stock GE-Proton11-3 archive is not the custom Forza Wine build. Fresh Prepare now rejects that known archive before acquisition when the dedicated FM tool is absent. Existing recovery records and trust hashes are unchanged.
- Issue [#8](https://github.com/volcmen/forza-motorsport-linux/issues/8): runtime writes and later tool mutations conflict with the original whole-tree Prepare fingerprint. The contributor fixes address specific retry/extraction/mode defects; they do not establish a complete replacement artifact or immutable composition workflow.
- `platform-check` discovers additional libraries for diagnosis only. It does not widen the mutating installer's primary-library policy or select an ambiguous prefix.
- A complete custom Proton build needs pinned source/SDK provenance, coherent Wine and Unix components, an artifact-specific trust manifest, and a real Steam prefix checkpoint. A successful compilation alone is insufficient.

Physical Steam Deck validation remains necessary for Microsoft sign-in, KDE Wallet,
Gaming Mode, controller/Steam Input behavior, actual microSD removal, suspend/resume,
graphics stability, performance, and gameplay. Containers isolate builds; QEMU tests
the OS and user-session environment. Neither substitutes for those device checks.

A complete `GE-Proton11-3-FM-test` build subsequently passed 26 Wine API regression
checks, with one opt-in invite-relay test skipped, in this installed SteamOS guest.
It used a fresh guest-local prefix and a read-only tool share as user `deck`.
See the [custom build record](custom-proton-build-2026-10-15.md) for its source,
artifact hashes, reproduced trace crash, and limits. The Steam client, GUI login,
installer transaction, and game were not exercised.
